# Project rules
- Read the same session-scoped verified home address for home display and checkout initialization; snapshot it once per checkout opening so address-book loads cannot overwrite the chosen delivery coordinates or subsequent checkout edits.
- Derive menu branch and detected area synchronously from loaded catalog data; GPS updates must not clear a valid pickup while reloading the catalog, to prevent layout flicker without cross-area fallback.
- Manage per-area restaurant coordinates through the existing branch editor and customer branch selection; do not duplicate brand listings for separate locations.
- Apply strict branch-area matching to every restaurant; never fall back to another area's branch during menu or checkout, and resolve checkout from the actual delivery-address coordinates so browsing state cannot select the wrong pickup.
- Use the shared cart pickup resolver for cart distance and fee previews, keyed by restaurant identity, area and customer coordinates; brand-level legacy pins must not select restaurant pickups.
- Reuse the shared Auth screen for restaurant login and existing owner-scoped dashboard; keep availability approval separate from paid-order preparation so payment flow remains unchanged.
- Defer database requests outside auth-state callbacks so the auth lock cannot stall signed-in pages; retain role loading before access decisions.
- Define explicit, least-privilege grants immediately after public table creation and preserve RLS; verify live changes with role-isolation tests because grants alone do not protect rows.
- Apply live permission changes through an additive migration; historical grant edits support clean replay but do not update already-applied databases.
- Keep KFC-only image presentation in KfcProductImage, with a neutral local fallback and contain fitting, so picture failures never substitute another product or change other restaurant displays.
- Steers uses a separate price_verified flag and Steers-only order validation while is_available controls visibility; other menus default to verified to preserve their behavior. Admin confirmation applies to all configured branches because the existing menu is brand-level.
- Keep Steers imagery isolated in SteersProductImage, label generated category pictures as illustrations, and never replace failed photos with another product.
- Burger King reuses the existing brand menu and branches; menuPriceVerification and a dedicated order guard block unconfirmed new prices while preserving existing positive prices. Admin confirmation is brand-wide because menus are shared by configured branches.
- Keep Burger King image failures neutral in BurgerKingProductImage so missing photos never display an unrelated product.
- Keep daily running-credit snapshots in an admin-read-only RLS table, never the browser bundle; retain UTC recording boundaries, precision and partial-day labels, and update only from authorized recorded-usage lookups because no documented automatic billing API is available.
- Resume customer pending-payment orders from owner-scoped authoritative reads; show the stored price/fee breakdown before Yoco handoff and use payment_status alone as paid evidence, so offline recovery and fulfilment status cannot bypass approval or payment confirmation.
- Serialize Yoco creation through service-only checkout leases and persist retry idempotency keys; queue paid notifications transactionally and retry them through the existing dispatch scheduler, so network failures cannot create competing checkouts or lose payment alerts.
- Enforce customer cancellation through row-locked unpaid-only RPCs and an order-write payment guard; keep payment verification service-authoritative and refund issuance outside customer grants so hidden controls cannot bypass cancellation protection.
